# Golden Trace — SaaS Marketing Site

This is the reference end-to-end example: one brief, run through the router,
producing a build plan, generated deltas on top of the starter, and a test
result. Its purpose is to validate that `router.json`, `kinds.json`,
`composition_matrix.json`, and `starters/nextjs-gsap-lenis/` actually compose
— if any of those files drift out of sync with each other in the future,
re-running this trace should be the first thing that catches it.

## 1. The brief (human input)

> "We need a marketing site for our B2B SaaS product. It's a single-page app
> built in Next.js. Six sections: hero, features, how-it-works, pricing,
> testimonials, CTA. No 3D assets. We want it to feel clean and modern, not
> cinematic. Performance matters but we're not on a strict budget — we're a
> normal SaaS company, not an e-commerce checkout flow."

Note `kind-ix` alone claims the `motion.limit.full-viewport-scenes` slot
(a subtle ambient canvas behind the hero, per `09_kind-ix_generative_art.md`) —
no other kind in this plan is a steady-state consumer of that budget, so
`composition_matrix.json`'s conflict check passes clean.

## 5. Composition check against `composition_matrix.json`

- **Init order:** kind-ix mounts *after* Lenis (step 4), kind-i's per-section
  reveals register after that (step 5) — matters here because the ambient
  canvas behind the hero could otherwise resize the document and invalidate
  ScrollTrigger boundaries if it mounted first.
- **Ambient-loop budget:** kind-ix contributes 1 ambient loop. Cap is 2. No
  conflict since no other looping kind is in this plan.
- **Concurrent budget:** kind-i staggers 6 section reveals with
  `motion.delay.item` (60ms) between them, so peak concurrent count at any
  scroll position stays under 8 even with kind-viii hover states active on
  already-revealed cards above the fold.
- **Engine conflict check:** View Transitions API (kind-vii) vs. Lenis
  (kind-i's scroll engine) — no conflict pair listed; these operate on
  different concerns (route change vs. in-page scroll) and don't fight.

## 6. Generated deltas on top of `starters/nextjs-gsap-lenis`

The starter already ships kind-i + kind-viii wired in. This trace adds two
things on top:

1. `components/AmbientCanvas.tsx` — new, implementing kind-ix per
   `09_kind-ix_generative_art.md`'s minimal snippet shape (p5.js instance
   mode, paused on `visibilitychange`, reduced-motion → static frame).
2. `components/PageLink.tsx` — new, implementing kind-vii per
   `07_kind-vii_page_transitions.md`'s minimal snippet shape (View
   Transitions API with Firefox fallback, modifier-click passthrough).

Both were generated by reading only the two `guide_file` paths listed in
step 4's `file_refs` for the narrative snippet shape — the routing decision
itself (whether to include these kinds at all) came entirely from
`router.json`, not from re-reading `01_kinds.md` prose.

## 7. Test result summary (what should pass)

Running `npm run test:e2e` against the composed page should produce:

- `tests/kind-i.spec.ts` — pass (6 scroll scenes, no layout-property
  transitions, ScrollTrigger cleanup verified, reduced-motion fallback verified)
- `tests/kind-viii.spec.ts` — pass (hover gating, focus-visible, touch targets ≥44px)
- `tests/a11y.spec.ts` — pass (no serious/critical axe violations)
- `tests/forbidden-patterns.spec.ts` — pass (CC1, CC6, CC10)
- **New, added for this trace:** `tests/kind-ix.spec.ts` asserting the
  ambient canvas has `aria-hidden`, is not the LCP element, and pauses on
  `visibilitychange`
- **New, added for this trace:** `tests/kind-vii.spec.ts` asserting
  modifier-click bypasses the transition handler and Firefox
  (`startViewTransition` undefined, emulated) falls back to plain navigation

## 8. What this trace validates about the kit itself

- The router correctly avoided forcing a full-viewport-scene conflict
  (it picked exactly one steady-state consumer: kind-ix).
- `kinds.json`'s `guide_file` pointers were sufficient to generate both new
  components without re-deriving anything already answered by the router.
- The composition matrix's init-order guidance was directly actionable
  (mount order was not ambiguous).
- The starter's existing test files did not need modification — only
  extension — confirming the starter's test-writing pattern generalizes to
  new kinds instead of needing a bespoke harness per kind.

If a future change to `router.json`, `kinds.json`, or the starter breaks any
step above, that's the signal those three have drifted out of sync.
